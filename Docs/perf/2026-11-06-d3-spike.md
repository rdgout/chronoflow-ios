# D3 render-server proof — 6 November 2026

Status: **needs a device; open**. No device trace or hitch result has been recorded.
OQ 4 has no Apple team yet. OQ 14's proposed budget is used (OQ 14 default assumed, confirm);
the reference ProMotion iPhone still needs to be named. Snapshot work precedes this proof by user
direction; rerun its assertions if the device proof changes the layer tree.

The first scene shows a separate window at `.normal + 1`, commits the opening tracks, then
flushes before creating the main window and SwiftUI root on the next main-queue turn. All
nonconstant tracks are CA keyframe animations with the same absolute media epoch, retained
under one animation key per property. The wordmark and plane glow are bitmap contents;
the sun and clipped outer halo are radial gradients. No display link or per-frame
main-thread update drives playback.

Points of Interest use subsystem `net.chronoflow.app.native`. `launch` and `first-commit`
begin at scene connection. `overlay-first-commit` is emitted immediately after the flush;
`root-first-layout` follows from the hosting controller's first layout. The hosted ordering
test asserts this sequence and checks the main window is still absent at the flush.
`session`, `ready`, `exit` and `intro` have paired APIs, host tests and production call sites
in readiness and Welcome. `launch` remains open while the overlay exists.

The stall flag blocks the main thread once, 300 ms after the overlay commit. Animation
submission precedes that block. A simulator presentation-layer comparison is useful for
correctness, but cannot establish real-device frame pacing or a ProMotion refresh rate.
Release parses both `-cf.mode ready` and `-cf.mainThreadStall`; the ready mode submits the
designed 1500–1900 ms exit independently of readiness. Release readiness always resolves signed out.
Slow/Welcome diagnostic modes, freeze, readyAt and readiness overrides remain Debug-only.
The isolated `ReadinessRelease` tests assert this contract, including the 500 ms stall value.

After configuring an Apple team in ignored `Config/Local.xcconfig`, use the selected device's
UDID and build/run a Release launch with the designed opening:

```sh
make generate
xcodebuild -project ChronoFlow.xcodeproj -derivedDataPath build/DerivedData \
  -onlyUsePackageVersionsFromResolvedFile -scheme ChronoFlow -configuration Release \
  -destination "platform=iOS,id=$CF_DEVICE_UDID" build
xcrun xctrace record --template 'Animation Hitches' --device "$CF_DEVICE_UDID" \
  --time-limit 5s --output build/d3-stall.trace --launch -- \
  "$PWD/build/DerivedData/Build/Products/Release-iphoneos/ChronoFlow.app" \
  -cf.mode ready -cf.mainThreadStall 500
```

Run once without the stall as a comparison, writing a different trace. Keep Low Power Mode
off. In Instruments, inspect 0–1500 ms relative to the first commit: require **zero hitches**
and approximately **8.3 ms** display/frame intervals during the animated opening. Verify
that the first-commit interval ends before the root's first layout, the 500 ms block actually
occurs, and the moon/sky/path continue through it. Record model, OS, team/signing setup,
trace paths, observed frame intervals and hitch counts here. If the proof fails, revisit D3
before further launch work, then rerun the snapshot assertions. Do not convert simulator results
into a device performance claim.
